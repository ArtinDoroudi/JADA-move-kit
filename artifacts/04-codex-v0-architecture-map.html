Where 17 hours of Codex went

Codex didn't write too little code. It wrote a lot of code into a design where every small rule needs about eight layers of plumbing. It also spent much of its time on rare branches and on fixing its own regressions. This page maps what exists, how a reporting year moves through it, and why the lines piled up.

The rule engine. It takes a frozen snapshot of a facility's answers and produces every threshold result, substance total and reporting duty. Process methods are hard-coded here (for example if electrode_class == "E310"). Its main function, evaluate_frozen_inputs, is 804 lines long by itself.

JADA reviewer accepts or rejects facts

admin · browser + workspace layer

Each answer the engine relies on must be accepted by a reviewer, and the acceptance is bound to the answer's exact version. There is a separate review module for each kind of fact: generators (EGU), prior reports, reporting metadata, monthly splits and other processes. This review step is one of the main sources of line count.

Inputs are frozen and the engine is called

Run is stored, then open items are resolved

workspace layer + admin

The run is saved with its digests. Anything the engine couldn't decide comes back as an open item. A reviewer closes each one with a manual figure, a declared method or a "not applicable" with a reason, and then the engine is run again. lifecycle_projection and pending_evaluator track which runs are current.

4 · Why the code got so big

Six reasons, with the evidence

1One rule needs code in eight layersThe generator (EGU) feature is about 7,300 lines for a question most welding shops answer "no" to.›

The plan says every fact must be frozen, versioned, reviewed by a person and traceable to a source. Codex followed that literally. So each new fact gets a database table, a migration, a Pydantic schema, a pure rule module, a review service, an API route, a frontend editor, a frontend model and tests. 2It went deep on rare branches before the common pathGenerators, monthly splits, prior-year comparison and condensable PM are all built. There are 12 emission-factor rows.›

A coding agent reads a file before editing it. When the file is 6,000 lines long, each edit costs a lot of context, and the agent forgets earlier decisions sooner. That's how you get bugs like the TypeScript error at admin.workspace.tsx:294, where workspaces is used but never defined.

5Methods are code branches, not dataEach new electrode, fuel or coating means more Python. It can't scale to oil and gas this way.›

The method layer isn't a table of factors run by a few generic calculators. Instead, each case gets its own function. _build_arc_e310_outputs is 322 lines for one electrode class. Adding E308, E316 and E7018 the same way would add hundreds of lines each, plus tests.

Now code per case

if electrode_class == "E310":
    return _build_arc_e310_outputs(...)  # 322 lines
# E308? new function
# E316? new function
# fuel oil? new adapter
# measured stack? not built

Lean data per case

method: activity_x_factor
process: P01 SMAW
activity: kg electrode consumed
factor: g Cr / kg  ← one CSV row
source: S07 AP-42 12.19
# 3 calculators cover most of P01–P28:
#   activity×factor, composition, mass balance
6AI code is verbose by default6,200 lines of schemas and defensive checks repeated in every module.›

Codex writes everything out explicitly. That means separate input and output schemas per feature (schemas/workspace.py alone is 2,811 lines), and the same rule split into a "pure" module in npri_v0/ plus a "review" module in workspace/. Examples are part4_method_reporting and part4_prior_comparison, which each exist in both folders. It also re-validates identity, version and digest in every function. Each choice is defensible on its own. Together they make the code roughly 2–3× longer than a person would write.

5 · Why only ~60%

The target was much bigger than it looks

"Welding" in the plan isn't one calculation. It's 28 process families, 128 questions, five NPRI Parts, 10 method types and 171 coverage branches, each of which must end in either a number or an explained "not applicable". Here is the coverage register Codex kept:

109 implemented
6
56 unsupported

Implemented means a route exists. It doesn't mean the numbers are reviewed: all factors are still marked published_unreviewed. The amber 6 are branches handled by manual entry.

6 · What this means

The amount of code is a design problem, not a speed problem

Keep

  • Freeze → evaluate → review → version → export lifecycle
  • Catalogue, coverage register and substance list as data
  • Threshold engine and Part 1–5 obligations
  • Digests and stale-run detection
  • Tests as a source of examples, after trimming

Rebuild

  • Methods as data rows + 3 generic calculators
  • One generic "fact review" component instead of a reviewer per feature
  • Split evaluator.py into stages with one file each
  • Split the two workspace screens into per-section routes
  • Cut scope to Beta A, then add rare branches behind a feature flag
