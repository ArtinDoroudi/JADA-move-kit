    regulation/notice_2025_2027/

    What stays the same

    • Reporting year 2026 under the 2025–2027 Notice, due June 1, 2027. The Notice prevails over the Guide.
    • Unknown is never zero, missing coverage is never "below threshold", and a published factor is not a JADA-approved method.
    • Manual results get the same trace and review as automatic ones. Approval, certification and filing stay separate human events.
    • The C1–C12 gates, the closure rules and the regulatory inventory still apply. v0's lifecycle, digest, export and threshold code is kept.

    Why change: v0 has a coverage problem, not a code-quality problem

    v0's lifecycle and safety rules are good. The trouble is shape: each new electrode, fuel or duty became new code. That made v0 large while it covered only part of welding.

    What those 733 positions are

    319non-zero numeric factors
    178published zeros (still evidence)
    89method-conditional, derived or reference cells
    147NA: computed by formula (cutting metals, PM2.5)

    Importing these is a reviewed spreadsheet import with a frozen manifest, not engineering work. In the new design that one import is the largest single coverage gain available.

    Six structural causes

    1. Every rule is an eight-layer slice

    Engine module, review service, schemas, resolution kind, digest hooks, routes, DTO, editor. EGU alone is about 7,300 lines.

    engine→review→schema→kind→digest→routes→DTO→editor
    2. Methods are code paths, not data

    _build_arc_e310_outputs is 322 lines that run for one method ID. 37 places branch on a method or process ID; 15 hard-code a "Pxx" literal.

    3. Each human decision got its own kind

    15 resolution payload kinds, each with a validator, review path, hooks and UI. They are all "a person states something, another accepts it".

    4. Rare branches came before common coverage

    EGU, low-hours oil-and-gas benzene and crude-battery branches were built while only E310 had factors.

    5. One file absorbed every feature

    Almost every checkpoint edited evaluate_frozen_inputs or service.py. Concurrent agents in god-files predict the repair rate.

    6. Generated code is verbose

    Tests often compute expectations by calling production helpers. The v0 plan itself says that "is not validation".

    0404-engine-pipeline.md

    The engine: eight pure stages in a fixed order

    This replaces the 804-line evaluate_frozen_inputs and its ~40 helpers. Each stage has its own frozen state type, so a stage cannot read something a later stage produces. Select a stage to see what it does.

    InputBundle + PinnedContent →bar = target size→ RunResult (digested)

    Why a fixed order works (no dependency graph)

    Some thresholds depend on emissions, and some outputs are only needed once a threshold is met. Stage 3 calculates everything it can, eagerly. Stage 7 decides what is required. A missing input for a reporting-only output stays non-blocking until a substance becomes reportable, so clients aren't asked for data that may turn out unnecessary.

    0303-domain-model-and-facts.md

    One fact model replaces 15 payload kinds

    Every human statement, from a client's electrode mass to JADA's method choice, is a fact keyed by a question ID. It has a typed value, a state, evidence, an author, a review and a dependency digest that makes it stale when its inputs change.

    v0 resolution kinds, each with its own validator, review service, routes and editor
    factapplicabilityinclusionmethod_assignmentmanual_contributionsource_inventorysource_scopeoutput_closurestack_decisionreporting_outputreporting_category_coveragereporting_metadataprior_report_acceptanceother_process_mappingfiling_workflow
    →
    # one schema, one review flow question: jada.method_eligibility subject: activity/a1 value: other_method1_justified state: known evidence: [consumable_log.pdf] author: jada:reviewer review: independent → accepted depends: sha256:… # goes stale on change

    Questions use prefixes: G, M, O, Pxx-n for client questions (v0 IDs preserved), jada.* for JADA decisions, F.* for filing fields. Review policies: none, jada, independent, practitioner.

    10 entity kinds, closed for every industry

    A new industry adds facts on these kinds, never a new kind. Quantities, compositions and capture rates are facts on an entity, so they get evidence, ranges and review.

    0505-calculators-and-factors.md

    Calculators are code; factors are rows; formulas are never evaluated

    A calculator is a small, pure, versioned function for one kind of math, usable by any industry. It uses Decimal only, never invents a missing input and records a full trace. A behavior change creates @2, and @1 stays registered so old filings replay.

    #CalculatorMathWelding packFirst needed

    Highlighted rows are what welding needs. Rule of two: a calculator gets a new mode, or is generalized, only when a second module needs it.

    Factor selection has exactly four outcomes

    applicable

    Exactly one row matches all keys and its conditions hold. The only outcome that supplies a number.

    → calculator
    needs_input

    A match key's fact is unknown, for example the electrode class.

    → client open item
    no_supported_factor

    No row for this key combination, or the row is not_available.

    → JADA: alternative or manual
    incompatible

    A row exists but a condition fails: control basis, filler, method variant.

    → JADA, with the failed condition

    A published zero is a real contribution of exactly 0 and closes the slot as evidenced_zero. Workbook "Other" rows are never a silent fallback; they need an accepted jada.method_eligibility fact.

    The routing grammar is closed

    Question visibility and method eligibility use equality and inclusion over facts. Anything numeric or date-based goes into a named, reviewed derivation, so YAML never turns into a programming language.

    eqinstatehas_entityallanynotarithmetic> <formula stringsfree expressions

    Invalid content (bad YAML, unknown calculator, unit mismatch, a factor row with no source, duplicate applicable rows) fails at load time in CI, never during a client run.

    1010-golden-cases-and-verification.md

    Golden cases are the specification

    v0 has 36.1k lines of agent-written tests that nobody can review. A golden case is a short file with a facility's inputs and the answer a qualified person expects. The practitioner signs the answer, and the engine must reproduce it exactly: exact Decimal values and exact sets of open items.

    How a method branch becomes automatic

    Importrows land as published_unreviewed
    Batch reviewunits, keys, basis, footnotes
    Reviewedjada_reviewed
    ≥2 caseswritten by hand, independent origin
    Signeddigest covers the case
    Automaticin the next pack version

    If a signed case fails after any change, the branch drops back to manual-supported and the release is blocked. A case whose expected values were pasted from an engine run is rejected.

    Kind of casePurposemetal_fab
    Module caseOne method path, eligibility branch or failure mode~70
    Whole-facility caseCross-process aggregation, destinations, lifecycle18
    Regulation boundary caseBelow, equal, above; ranges; qualifiers; holds~60
    Calculator caseDimensions and arithmetic, official examples8–15 each
    1111-lifecycle-freshness-and-replay.md

    Lifecycle kept; every run pins its content

    v0's lifecycle is the best-tested part of v0 and stays as it is. What's new is that each run records the exact notice, pack, factor table and calculator versions it used, by digest.

    stateDiagram-v2
  direction LR
  [*] --> Draft
  Draft --> ClientHandoff: request review
  ClientHandoff --> Draft: JADA returns items
  ClientHandoff --> RevisionDraft: revision from fresh run
  RevisionDraft --> Approved: independent approval
  Approved --> Certified: authorized certifier
  Certified --> Completed: annual actions recorded
  Approved --> Draft: upstream change, stale
  Completed --> [*]
    • Re-pinning is explicit. A workspace keeps its pack and notice versions until JADA re-pins it and reviews a diff of what changed. Filed revisions never re-pin.
    • Replay works years later. Old calculator and rule versions stay registered, so a 2026 filing reproduces byte-for-byte after the engine moves on.
    • Freshness is generic. One dependency-digest check covers every fact, instead of hooks per feature.
    • Export adds a content appendix listing every factor row and rule version behind the numbers. An export is still not a filing.

    1313-delivery-cycles.md

    Delivery cycles N0–N9

    Assumes 2 developers and a part-time HSE practitioner (about 0.5 FTE). The fixed point is June 1, 2027. Select a cycle to see its work and exit gate. dates are estimates

    Rules for every cycle

    • One pack or platform theme per cycle; the next starts only when the gate passes.
    • A gate is practitioner-signed golden cases plus listed checks, never a line or test count.
    • Feature freeze during filing seasons, mid-March to June 1.
    • Each PR or agent task is a reviewable slice of about 1–3k lines, committed before the next starts.
    • Report each cycle: automatic / manual / unsupported branches, factor rows by review state, signed cases, repair share of merged PRs (v0: 39 of 104; target under 15%).

    The real test: adding pits and quarries

    If the architecture works, a new industry is mostly practitioner work. Engineering shows up only for math no calculator does yet. Pits and quarries needs no new calculator. illustrative; ECCC sources identified, not yet read in full

    • The applicability rules are already data: production ≥ 500,000 t removes the employee-hours gate (§1(1)(a)); a site whose only activity is a pit or quarry below that is excluded (§1(2)). The pack adds one question and one derivation that classifies production.
