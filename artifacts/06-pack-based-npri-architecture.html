Pack-Based NPRI Architecture
Proposal · JADA NPRI platform · Nov 2026

Write the engine once. Add industries as data.

The proposal is to split the system into an engine that never knows which industry it's running, and industry packs that hold the questions, factor tables and worked test cases. Adding oil and gas then means writing a pack, not 40,000 lines of Python and React. Practitioners can review a pack, and engineers only review the engine.

~25–30klines of app code for 100% of welding, vs ~65k in v0 for ~60%
~0.2klines of code per new process family, vs ~3.9k in v0. The rest is data and test cases.
14calculators cover every industry. Welding needs 4 of them.
1fact model and review flow, replacing 6+ per-feature review modules
Codex already got halfway there. The question catalogue (catalogue_2026.json, 28 processes and 128 questions) and the factor file are already data. A factor row even has its activity basis and formula. But the engine ignores that and branches on IDs: evaluator.py:2294 _build_arc_e310_outputs is a 322-line function that only runs when method_id == "arc-listed-v1". The proposal is mostly to finish what the data files started.

2 · Seven design rules

What changes compared with v0

1Methods are calculators plus data rowsA new electrode, fuel or coating is a CSV row, not a function.›
v0 todayEach case has its own code path. E310 welding is a 322-line function bound to arc-listed-v1@1. Blasting, natural gas and organics each have their own adapters in process_methods, organic_methods and combustion_adapter.
ProposedA registry of calculators (activity_x_factor, composition, mass_balance, …). A module names its calculator and points at a factor table. E7018, E308 and E316 become rows in the same CSV.
The factor file's formula string should become a calculator ID plus parameters. Never evaluate formula strings from data.
2Industries are versioned packsOne folder per industry, built from shared modules plus its own.›
v0 todayWelding knowledge is spread across the catalogue JSON, the coverage JSON, the factor JSON, evaluator branches and frontend editors.
Proposedpacks/metal_fab/pack.yaml lists the shared modules it uses (welding, coating, degreasing, boilers) and its own. A pack has a version, so a filed report always knows which pack version produced it.
3One fact model, one review flowEvery answer is a fact with a schema, evidence, a version and a reviewer.›
v0 todaySeparate review services for generators, generator details, prior reporting, reporting metadata, monthly split and other processes. Each has its own schemas, API and a 1–2k-line editor. The generator feature alone is about 7,300 lines.
ProposedOne facts table keyed by question ID. The question's schema in the pack validates the value. The same review screen accepts or rejects any fact. A new kind of question needs no new table, API or screen.
4The engine is a list of small, pure stagesEight files under ~300 lines each, instead of one 5,945-line file.›
v0 todayevaluate_frozen_inputs is 804 lines and calls about 40 helpers. Every feature edits it, which is where many of the 39 repair checkpoints came from.
ProposedEach stage takes a typed, frozen state and returns a new one, and each can be tested alone. A feature lives in one stage, or in a calculator, or in data.
5The UI is generated from the packOne form renderer instead of a hand-written editor per feature.›
v0 today+28.9k frontend lines. That includes two route files of 6,004 and 4,846 lines plus editors for metadata (2,292), generator details (1,357), prior comparison (1,097) and so on.
ProposedQuestion types (yes/no/unsure/other party, number with unit, table, file) render from the pack. You write custom screens only for genuinely different interactions, about 3–5 in the whole product.
6Regulations are data, per Gazette noticeWhen the 2028 notice lands, add a new folder. Don't edit code.›
v0 todayThe substance list is already data (substances_2026.json), but obligations and Part rules are partly in code, in reporting_obligations.py (1,031 lines) and reporting_metadata.py (961 lines).
Proposedregulation/notice_2025_2027/ holds substances, thresholds, Part rules and filing fields. The reporting year selects the notice.
7Golden cases are the spec and the review unitPractitioners review expected answers. Nobody reviews 75k lines.›
v0 today31k lines of tests written by the agent. They prove the code does what the agent intended, not what the regulation says.
ProposedEach module ships with 2–5 sample facilities and their expected kg, written or checked by an HSE practitioner. The engine must match them exactly. Code review then shrinks to engine and calculator changes.

core/calculators/activity_x_factor.py written once
@calculator("activity_x_factor", version=1)
def run(activity: Quantity, factor: FactorRow) -> Contribution:
    kg = activity.to("kg") * factor.per_kg()
    return Contribution(
        substance=factor.substance,
        medium=factor.medium,
        kg=kg,
        rating=factor.rating,
        trace=[activity.ref, factor.ref],  # every number is traceable
        flags=factor.flags,                # e.g. unresolved basis
    )

4 · Adding an industry

Mostly practitioner work, rarely engine work

List the processesFrom ECCC sector guidance and real sites. Mark each as a shared module or a new one.HSE · 2–5 days
Write questions and factor rowsModule YAML and CSV, with a source and rating on every row.HSE + dev · ~1 week per 4 modules
Write golden cases2–5 sample facilities per module with expected kg and open items.HSE · ~0.5 week per module
Validate and sign offThe pack validator checks schemas and coverage. Cases must match exactly before the pack ships.automatic + HSE sign-off

Engineering work appears only when a pack needs math no calculator does yet, such as flares for oil and gas or tailings for mining. That's 10 calculators across all 16 industries after welding's 4. Rule of two: don't generalize a calculator until a second pack needs it.

5 · Growth

How code grows as industries are added

Lines of application code, with industries added in the order from the priority plan. "v0 style" assumes ~3.9k lines per process family and no reuse, which is what v0 produced. "Pack-based" adds mostly data. These are rough estimates, not measurements.

7 · Trade-offs

What this costs and how to contain it

Slower first monthBuilding the generic engine and fact model takes about 6 weeks before any new feature ships.Contain it: v0's lifecycle code is kept, and the E310, blasting and natural-gas paths act as the acceptance test.
The YAML turns into a programming languagePacks start growing conditions, loops and formulas.Contain it: data only picks a calculator and its inputs. Logic goes in calculators, which are code and get code review.
Some industries don't fitRefinery speciation and Part 1B tailings need special math.Contain it: they get their own calculators. That's still about 10 calculators in total, not one engine per industry.
Over-generalizing too earlyBuilding abstractions for industries nobody has bought.Contain it: the rule of two. Generalize only when a second pack needs it, and build Wave 4 only for a paying client.
