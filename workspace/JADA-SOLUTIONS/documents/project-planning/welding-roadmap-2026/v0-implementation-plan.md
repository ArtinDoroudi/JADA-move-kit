# Welding NPRI SaaS v0 implementation plan

Prepared 2026-11-04. Status: architecture contract for implementation and review; not a claim of practitioner approval, numerical validation or production readiness. Pilot year: 2026. JADA reviews and files a complete facility package. This implements the facility scope in the [roadmap](README.md), [catalogue](process-catalogue.md), [questionnaire](questionnaire.md) and [source register](sources-and-decisions.md).

## Scope and implementation contract

All 28 process families must be discoverable, persisted and resolvable through an actual client and JADA journey. Each present operation receives an automatic method or a structured evidenced manual determination. A generic form that accepts an unexplained final number is not manual support. Missing implementation, evidence or interpretation remains a blocker. Build the complete workflow now; promote each automatic method only when its source, exact scope and independent numerical tests pass. No placeholder claim of universal calculations is acceptable.

Retain `ReportingPeriod.id` as the facility-year identity and existing account, facility, SDS, purchase, extraction, matching and normalization APIs. Add the versioned workspace below. The legacy calculation table is not the v0 engine: it applies universal constants, uses midpoint estimates and replaces results. Legacy extraction `pipeline_status` is not regulatory readiness. Keep old reports readable, but new v0 reports route through the workspace and legacy finalization cannot bypass its gates.

### Stable ownership and persistence

Implement the following SQLAlchemy tables with a new Alembic migration. Relational rows enforce tenant ownership, immutable versions and workflow; typed JSONB is suitable for bounded case collections, provided Pydantic validates all nested fields and references. Do not accept arbitrary unvalidated dictionaries as calculation inputs.

| Table | Required fields and invariant |
|---|---|
| `facility_workspaces` | `id`, unique `reporting_period_id`, `schema_version`, `version` integer, `inputs` typed JSONB, `created_at`, `updated_at`; row locking plus expected-version concurrency check for every mutation |
| `workspace_resolutions` | UUID, workspace FK, subject type/ID, kind, typed payload, author, authored workspace version/dependency digest, review status, reviewer/time/reason; reviewed records immutable, replacements supersede |
| `workspace_evidence` | UUID, workspace/owner FKs, kind, source record IDs and locator, original filename, media type, content digest, immutable blob path or frozen structured record, uploader/time; immutable content, append new version |
| `workspace_runs` | UUID, workspace FK/version, canonical input/source digest, ruleset/method versions, frozen input and source manifest, typed result JSONB, engine version, created actor/time; immutable |
| `workspace_revisions` | UUID, workspace FK, revision number, run FK, input/source digest, complete frozen package JSONB, manifest digest, creator/time; immutable content; approval state comes from events |
| `workspace_events` | UUID, workspace FK, optional revision FK, event type, actor, timestamp, payload; append only; includes request-review, return, approval, certification, filing, supersession and reopen |

Versioned source/rule/method/factor catalogues may initially be repository JSON loaded into immutable typed Python objects; mutable database rule administration is not needed for v0. Each run embeds the precise records it used. Clients cannot upload executable rules or select arbitrary formulas. Resolve changes through a reviewed code/data release.

### Typed inputs v1

`WorkspaceInputs` contains these named collections. IDs are UUID strings created by the API or validated client UUIDs. All references are checked within this workspace and its authorized owner. Date intervals use ISO dates; amounts use decimal strings, never binary floats in accepted calculation records. Unknown values remain null with an explicit state; numeric zero is valid only with an accepted basis.

- `facility`: year 2026, confirmed boundary/annual coverage, ownership dates, operating/shutdown schedule, prior filing history, public/technical/certifier contacts, owner/operator/parent identifiers, industry/activity description, pollution-prevention details. Existing facility snapshots prefill facts but require annual confirmation.
- `employee_hours`: employee worked/overtime, vacation/sick, nonduplicated owner and contractor operations hours, category evidence and unresolved categories. Never infer hours from headcount.
- `screens`: exactly P01–P28, each `answer: yes|no|unknown|other_party`, confirmation actor/time and optional explanation/evidence; no preselected No. `other_process` is G17 with the same uncertainty behavior. P28 needs location/responsibility resolution.
- `answers`: `{question_id, instance_id?, state: provided|unknown|unavailable|not_applicable, value, unit?, period_start?, period_end?, basis?, evidence_ids[]}` validated against a checked-in question catalogue. Catalogue supplies G01–G17, M01–M08, O01–O08 and every Pxx-n question. Conditional questions are not silently removed from saved history.
- `activities`: `{id, family_id, subtype?, label, equipment, location, period_start, period_end, physical_operation_id, material_use_ids[], control_ids[], outlet_ids[], stream_ids[], evidence_ids[]}`. Multiple family labels can describe one physical operation without duplicating its contributions.
- `facts`: `{id, subject_type, subject_id, key, state: known|range|unknown|unavailable, value?, min?, max?, unit?, basis?, period_start?, period_end?, evidence_ids[], provenance: client|extracted|derived}`. Acceptance and interpretation are staff resolutions, not client-editable flags.
- `materials`: `{id, label, inventory_product_id?, sds_document_id?, purchase_line_ids[], opening_stock?, receipts?, returns?, transfers_in?, transfers_out?, closing_stock?, annual_use?, unit, usage_basis, composition_facts[], evidence_ids[]}`. Composition uses stable substance/group IDs and mass/volume basis. Purchases do not automatically equal use.
- `allocations`: `{id, material_id, activity_id, quantity, unit, kind: consumable_split|fuel_split, evidence_ids[]}`. Reconcile splits with accepted annual use and show the unallocated balance.
- `material_flows`: `{id, batch_id, material_id, from_activity_id?, to_activity_id, quantity?, unit?, loss_stream_id?, evidence_ids[]}` for sequential workpiece lineage. These are not new purchased quantities or consumable splits.
- `controls`: `{id, label, type, source_activity_ids[], pollutant_scope[], capture_facts[], removal_facts[], operating_segments[], bypass_facts[], outlet_ids[], residue_stream_ids[], evidence_ids[]}`. Percentages constrained to 0–100; capture is distinct from removal.
- `outlets`: `{id, label, route: fugitive|outside_vent|indoor_recirculation|mixed|other|unknown, activity_ids[], control_ids[], geometry_facts[], evidence_ids[]}`. Basic routing always; detailed stack facts only when required.
- `streams`: `{id, label, kind: waste|recycling|water|retained_residue, activity_ids[], quantities[], composition_facts[], destination, recipient?, evidence_ids[]}`. Destination is a controlled reporting taxonomy or unresolved; gross stream weight is not constituent mass.
- `incidents`: dated source/material/released/recovered quantity facts and destination links.

Use explicit nested models for each entry, reject duplicate IDs, invalid references, nonfinite/negative quantities, reversed ranges/dates, incompatible units, concentration outside 0–100%, duplicate annual screens, and allocations beyond accepted use. A draft may save unknowns; invalid arithmetic cannot be accepted. Keep technical decisions outside client inputs.

### Decision, contribution and evaluation outputs

Every decision uses one envelope:

```text
decision_id, subject_type, subject_id, rule_id, rule_version
state = resolved | needs_input | needs_interpretation | unsupported
value = typed result only when resolved; otherwise null
input_references[], source_references[], reasons[]
requirements[] = {id, key, owner: client|jada|developer, kind,
                 subject_id, question_id?, reason, evidence_options[],
                 blocking, dependent_decision_ids[]}
```

Requirements deduplicate by workspace/year/subject/fact-or-method key. Missing software is assigned to JADA/developer, never disguised as a question asking the client for a factor. Requirement IDs are stable between identical runs.

`Contribution` contains `id`, `source_activity_id`, `physical_operation_id`, `material_or_stream_id?`, `substance_id`, `chemical_basis`, `quantity_kind: material|assessment|release|disposal|recycling`, `quantity` or range, `unit`, `destination?`, `assessment_basis?`, `method_id/version`, `factor_ids[]`, `input_refs[]`, `source_refs[]`, `inclusion_decision_id`, `manual_resolution_id?`, `trace_steps[]`, `aggregation_key`. Excluded rows remain visible. Automatic and reviewed manual outputs have this same contract. Group membership is explicit; CAS is optional and never the primary identity.

`Evaluation` contains `run_id`, `workspace_version`, `input_digest`, `source_digest`, `ruleset_version`, `decisions[]`, `requirements[]`, `contributions[]`, `assessments[]`, `activity_coverage[]`, `rule_family_coverage[]`, `readiness`, and `warnings[]`. Each assessment names the basis, comparator and unrounded boundary, contributing/excluded IDs, outcome (`met|not_met|pending|not_applicable`) and reasons. `readiness` independently supplies `can_request_review`, `can_approve`, `can_file`, and named blockers. Extraction completion must not populate these booleans.

### HTTP contract v1

Base `W = /api/v1/reporting-periods/{period_id}/workspace`. All workspace endpoints use existing authentication plus owner-or-staff access; mutations additionally enforce actor capability. JSON responses use decimal strings. `expected_version` is mandatory on mutations of current workspace state. Version conflict returns HTTP 409 with current version and a reload action; domain invalidity returns 422 with field paths; unauthorized records return the existing consistent access error. Never expose another tenant's data in an error.

| Route | Request / response and role |
|---|---|
| `GET /api/v1/workspace-catalogue?year=2026` | Process/question catalogue, supported methods, source/rule versions, enums and coverage descriptions; authenticated |
| `GET W` | Create-on-explicit-write only; returns current inputs/version, latest run summary, latest revision state, stale flag, relevant upstream references, allowed actions; absent workspace returns 404 |
| `POST W` | `{}` initializes from this authorized period and available records, `201 WorkspaceOut`; idempotent existing response permitted; owner/staff |
| `PUT W/inputs` | `{expected_version, inputs}` replaces validated current client inputs; increments version, logs change; owner/staff; cannot set reviews, decisions or results |
| `POST W/import-records` | `{expected_version, purchase_line_ids?, inventory_selection_ids?, sds_document_ids?}` imports candidate facts with exact source revisions; preserve accepted corrections, return conflicts; owner/staff |
| `POST W/evidence` | Multipart file + source/locator metadata, or separate structured evidence endpoint; private stored content, size/type checks, SHA256; owner/staff |
| `GET W/evidence/{id}` | Authorized metadata/download; never a public storage path |
| `POST W/evaluate` | `{expected_version}` freezes current sources, runs deterministic evaluator, persists immutable run; owner/staff; missing facts produce 200 pending results, not fabricated zeros |
| `GET W/runs/{run_id}` | Full historical evaluation with freshness relative to current case; owner/staff |
| `POST W/resolutions` | `{expected_version, kind, subject_type, subject_id, dependency_refs, payload, evidence_ids, reasoning, source_refs}`; staff only; kinds include fact acceptance, inclusion/exclusion, applicability, method assignment, manual calculation, stack decision, filing workflow |

Catalogue and DTO definitions are owned by backend; frontend follows them. A compact compatibility adapter can expose existing report status, but regulatory readiness always comes from workspace evaluation. New UI uses these routes; no route should save only browser state.

### Freshness and retention contract

On evaluate, request-review, approval, certification, filing and current-package export, compute a canonical manifest over current workspace inputs, approved resolutions, all referenced live purchase/inventory/normalization/SDS records, accepted evidence digests, ruleset and method versions. Canonicalize object keys, stable-sort entity arrays, serialize decimals exactly, exclude transient timestamps. A changed manifest invalidates the current calculation/approval and opens a new draft. Mutation hooks are useful for immediate notices; they are insufficient as the only protection.

Immutable revisions retain complete source facts and required evidence content, not dangling IDs or paths to mutable/deletable uploads. Reuse content-addressed private blobs with reference protection or make protected snapshots. Historical exports remain possible after current edits, clearly labeled with their original revision and status; filing the stale revision as current is rejected. Deletion of a live SDS cannot delete evidence retained by a filed package. A correction creates a new revision and filing action; it never edits history.

### Immediate implementation partition

1. Backend foundation owner: migration, typed models/DTOs/catalogue, auth protection, CRUD/import/evidence, source digest, resolution/event persistence, immutable run/revision primitives. Own `workspace` API/service/schema/model files. Build pending-only evaluator adapter until deterministic engine is integrated; never return a fake success.
2. Backend calculation owner: pure rule/method engine, checked-in source/rule/factor data and numerical fixtures. Receive typed frozen inputs; return Evaluation. No HTTP or database side effects. Own `services/npri_v0/` and associated tests/data.
3. Frontend owner: client workspace and all conditional process screens, JADA queue/resolution/review/package UI, API DTO adapter, navigation and stale/conflict handling. Follow the agreed route contract and existing design system.
4. Integrator/reviewer: approve contract changes, connect engine and persistence, extend legacy mutation/finalization protections, run migration/security/full-journey checks, inspect numerical scope and stop false completeness.

These are ownership boundaries, not permission to reduce the full scope. Agents must send proposed contract changes before changing shared DTO names or shape. The parent coordinates assignments and worktree safety.

## Regulatory coverage implementation

Maintain one executable coverage matrix keyed by reporting year, rule family and branch. Entries carry source locator, authority edition/digest, `implemented|manual_supported|unsupported`, required facts, tested fixtures and interpretation status. The screen inventory is not a substitute for this matrix. Start identity reconciliation from the supplied 2025–2027 workbook, joining by stable identity within each language, then verify qualifiers and groups against the controlling source.

The [2025–2027 Notice](https://gazette.gc.ca/rp-pr/p1/2025/2025-03-08/html/sup1-eng.html) is the governing source for the 2026 case. Use its Schedule 3 for applicability and threshold branches and Schedule 4 for report content; retain a separately versioned filing-field map. The 2026 deadline is June 1, 2027. This plan does not assert that an exhaustive amendment audit has been completed. Recheck the [official notices index](https://www.canada.ca/en/environment-climate-change/services/national-pollutant-release-inventory/report/legal-requirements-gazette-notices.html) when releasing rule data and filing.

| Branch | Required v0 behavior and test obligations |
|---|---|
| Facility and employee/activity applicability | Separate facility boundary, annual employee-hour calculation, exceptional activities, specific Part rules and exemptions. A low-hours answer does not globally stop screening. Store present/absent/unknown for every applicable exceptional-activity branch. Unknown boundary/contractor allocation remains pending. |
| Ordinary Part 1A | Execute accepted material/composition contributions with exact concentration treatment, inclusion/exclusion and group/chemical qualifiers. Test threshold equality, by-products and ranges. An unconditional mass × SDS percentage implementation is insufficient. |
| Part 1B | Per-substance/group mass and concentration rules; no common threshold substituted. Verify cobalt, lead/lead alloy exclusions, mercury, chromium species and newer group identities as applicable. Unsupported special treatment produces a named resolution. |
| Part 1C | Screen listed PFAS with exact identity and source completeness. Missing SDS disclosure cannot prove absence. Support validated per-substance tests; missing supplier identity/composition goes to evidence/manual review. |
| Part 2 | Model the relevant manufactured-incidental/released/transferred assessment basis and special activity path separately from ordinary purchased mass. Full branch presence/absence is reviewed even when the welding calculator lacks these outputs. |
| Part 3 | Resolve specified industrial activities from the complete authoritative activity list, not a keyword match on “arc.” Positive/uncertain specialty operations require structured assessment and appropriate units/speciation; no purchased-chemical threshold shortcut. |
| Part 4 | Sum applicable air releases by contaminant/fraction over all sources after rule-scoped exclusions. Evaluate relevant equipment-only and low-hours paths. Keep TPM, PM10 and PM2.5 as distinct nested fractions, not additive members of one total. |
| Part 5 | Evaluate individual VOC/group pathways with their own triggers and exceptions; do not install a universal total-VOC prerequisite. Reconcile overlap with Part 1 and total VOC without summing them as distinct physical emissions. |
| Individual stacks | Retain source-to-outlet map; assess detailed stack criteria separately from facility air totals. Existing I03/I04 conflicts require exact controlling-source resolution; unknown temperature cannot be coerced to ambient/zero. Manual-supported initially. |
| Notifications and annual closure | Prior filing and current determination select report, does-not-meet-criteria notification, ownership/closure action, update, voluntary report or evidenced no-filing determination. Multiple actions can coexist. Zero output after an applicable threshold is met does not erase the reporting action. |

Pure functions should be small and branch-specific: `assess_facility`, `resolve_identity`, `assess_contribution_treatment`, `select_method`, `evaluate_method`, `aggregate_assessment`, `assess_threshold`, `evaluate_output_requirements`, `evaluate_readiness`. They consume a frozen typed context and return decisions/contributions. Use a declared dependency order; there is no requirement for a graph database or expression language. Some assessments depend on emissions, so do not force all threshold tests ahead of all release methods.

### Partial knowledge and ranges

Store lower/upper accepted bounds where justified. A complete interval entirely below a boundary can support `not_met`; an interval crossing it is pending unless an approved rule-specific estimate policy resolves the uncertainty. A known lower bound already at/above an inclusive threshold can support `met` even while other contributions remain unresolved. That does not mean the final report quantity or whole facility package is complete. A partial sum below threshold never supports an authoritative negative conclusion.

Track physical-source completeness separately from numeric comparison. A method producing manganese and PM does not establish absence of every other relevant pollutant. A reviewed candidate-substance inventory must consider accepted product chemistry, process-generated species, fuels, incidents, waste and water; database matching to disclosed CAS rows alone is insufficient.

Controls are pollutant- and segment-specific. Validate source capture, device removal, bypass and operational coverage separately. Do not subtract captured particulate from a VOC result, reduce an already-controlled factor again, or label indoor recirculation as a documented zero environmental release. Route collected material to a residue/reuse stream without assuming its constituent mass equals the mass of gross collected waste.

## Automatic-method scope and numerical gates

Method registry entries must name: method ID/version, supported process/subtypes, required facts and units, applicability/exclusions, factor-source table/cell/footnotes, coefficients and dimensions, controlled/uncontrolled basis, output definitions, group/species mapping, rounding, benchmark fixtures and software/practitioner review state. A factor has a source-specific key, not just a substance ID. Preserve source units alongside normalized units.

The initial automatic target is the following concrete scope. Broader cases remain explicit manual tasks until a comparable method card passes. Methods cannot be marked approved merely because this table names them.

| Method ID | Automatic target and boundary | Numerical gate |
|---|---|---|
| `arc-listed-v1` | Enumerated process/electrode rows actually present in the official welding workbook; begin SMAW E310-16 and extend exact mapped classes. No product-name fuzzy match decides the factor. | Reproduce sourced E310-16 material-assessment and release examples; independently audit extracted factor rows and units. Unknown class yields lookup requirement. |
| `arc-composition-v1` | Supported named arc process with filler and reviewed eligibility for the published composition alternative; reliable fractions required. Autogenous GTAW/PAW is not covered by filler mass. | Check GMAW alternative without premature rounding; metal fraction applied once, chromium split explicit. Eligibility refusal and missing composition tested. |
| `cutting-listed-v1` | Explicit workbook-supported thermal/cold subtypes only; begin oxy cutting with active-time segments and time-weighted composition. Shears/waterjet/unlisted mechanical cutting do not inherit it. | Independent active-hours → minutes conversion; unequal-material-duration case; assessment mass distinct from release time; cutting-grinder overlap rejected. |
| `spray-listed-v1` | Explicit workbook feedstock/process combinations; begin plasma spray with mass-weighted composition. Ordinary paint is P13. | Distinguish factor per feedstock mass from factor per constituent mass; composition neither omitted nor applied twice; particulate/metal relationship checked. |
| `blast-dry-sand-v1` | Published uncontrolled dry-sand scope after AP-42 conditions and abrasive-use basis are verified; explicit source wind-class selection for TPM. | `solvent-balance-v1` | Nonreactive, defined-boundary solvent use with accepted composition and accounted inventory, product retention, recovery and waste solvent. | `liquid-coating-balance-v1` | Component-based liquid coating/thinner/hardener with accepted as-applied density/composition, volatile ingredient behavior, retained/waste/recovered fractions and applicable control. | Two-component recipe with separate thinner and cleaning product; wet volume → component mass → constituent mass; booth particulate collection must not remove VOC. | `external-natural-gas-v1` | Named natural-gas external-combustion equipment/factor rows from applicable AP-42 1.4 edition, including capacity/burner/control/volume conditions. | `fuel-oil-heater-v1` | Named oil-fired heater/boiler configurations when official calculator/table dimensional issue I05 is resolved; otherwise structured manual pending rather than guessed scale. | Reconcile per-thousand-US-gallon source units, litres conversion, sulfur/heating-value dependencies and corresponding workbook output. |
| `measured-stream-v1` | Representative accepted concentration/flow-time or constituent-fraction/mass records for specific water/waste boundary and destination. | Units, wet/dry basis, segmented annual coverage, detection limits and representative-data decisions tested. Unsupported sampling interpretation remains manual. |

These method targets use the [ECCC welding guide and calculator](https://www.canada.ca/en/environment-climate-change/services/national-pollutant-release-inventory/report/tools-calculating-emissions/arc-welding-cutting-spraying-calculator.html), [abrasive blasting method](https://www.canada.ca/en/environment-climate-change/services/national-pollutant-release-inventory/report/tools-calculating-emissions/fugitive-dust-emissions-abrasive-blasting.html), and source register S08/S12/S13. The solvent/coating test is a synthetic arithmetic fixture, not an official universal formula. A balance boundary cannot count internally recycled solvent as both a new input and an external recovery output.

Use exact Decimal arithmetic and compare unrounded quantities against thresholds. Unit conversion tests should be exact where the conversion is defined exactly. Method benchmark tolerances must be set from the source's precision: retain high precision internally and separately test displayed rounding. The old guide's rounded examples may differ from full-precision calculation; record the discrepancy rather than modifying the engine to mimic intermediate rounding.

The numerical test suite must have two independent expected-result origins: hand-worked units/balances plus an applicable official example or recalculated workbook when available. Tests that merely call the production helper to create expected results are not validation. For each factor import, check source-row count, keys, null-versus-zero, allowed ranges and checksum, and manually inspect representative and unusual rows. No live LLM participates in arithmetic or fixture expectations.

## Manual work is an accountable method

A manual result requires all of: named source/activity/output scope; reason automatic methods do not apply; method/source and exact locator; eligibility rationale; accepted input facts and units; evidence content; calculation steps or attached reproducible workbook/report; output quantities, identities, basis and destinations; uncertainty and assumptions; author and reviewer identity/time. A decision of no contribution additionally requires its rule-specific reasoning and evidence. It must not simply mark the process “done.”

The staff editor should support repeatable output rows and typed operands, evidence attachments, source links and rationale, with a preview of the resulting contributions and affected assessments. Provide separate actions to save a proposal, accept/reject it and rerun. Require a reviewer different from the calculation author for final manual acceptance in the pilot candidate; trusted test fixtures can provision two staff users. This is a product review safeguard, not a claim that the Notice mandates two staff users.

An accepted resolution is valid only for its specified dependency digest. Changing its source material, quantity, composition, annual period, method, output scope, controls or evidence makes it stale. Staff cannot dismiss unresolved required outputs through a generic override. Global “not applicable” assertions require a scoped, sourced decision and still preserve unaffected obligations.
